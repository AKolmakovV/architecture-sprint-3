# ✅ Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удаленно включать/выключать отопление и устанавливать желаемую температуру через веб-интерфейс
- Система поддерживает только синхронное взаимодействие
- Пользователи не могут самостоятельно подключить новые датчики или другие компоненты отопительной системы, требуется выезд специалиста
- Система работает только с отоплением

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру через веб-интерфейс
- Система поддерживает только синхронное взаимодействие запрос-ответ

### 2. Анализ архитектуры монолитного приложения

Технический стек:

 - Backend: Java
 - База данных: PostgreSQL
 - По всей видимости имеется Веб-Приложение, делаем допущение JS/HTML/CSS

Архитектура приложения:

1. Перед нами монолитная архитектура с синхронным взаимодействием
2. Проект использует Docker контейнеризацию для доставки и развертывания
3. Также особенностью является то что текущее приложение является stateless
4. Аутентификация\авторизация отсутствует

### 3. Определение доменов и границы контекстов

##### ***Текущая картина (из описания и исходников)***

#### **Управление отоплением** 

Компания изначально занимается только отоплением что и формализует данный домен. Мы не имеем информации о существовании дашбордов или систем мониторинга, а значит не создаем отдельный домен, все укажем в этом, что и отражает имеющийся сервис HeatingSystemService.

**Функции:**

1. Настройка целевых показателей температуры
2. Просмотр текущей температуры
3. Включение или отключение отопления
4. Подключение датчиков или других устройств отопления (производится специалистами компании)

**Границы контекста:**
Не формализую, система монолитная, решает весь круг возможных задач, даже на уровне сервисов, явного разделения на другие домены не имеет, компания настраивает систему для пользователя и оставляет ее "как есть" эта часть бизнеса не отражена в техническом решении.

### **4. Проблемы монолитного решения**

- Сложности и ограниченность в масштабирования по причине того что на данный момент решение имете монолитную архитектуру (в даннном случае из за того что придется масштабировать разом весь функционал приложения, либо до определенного предела наращивать мощности сервера, либо в какой то части можно отмасштабировать БД)
- Синхронное взаимодействие также может влиять на производительность не в лучшую сторону (например при большо количестве запросов)   
- Синхронное взаимодействие также может влиять на актуальность некоторых данных, как пример, мы можем получать температуру только по запросу, для поддержания актуальности нам потребуется отправлять регулярные запросы, что дополнительно будет нагружать систему      
- При анализе приложения было выявлено отсутствие механизмов аутентификации что является проблемой безопасного использования
- Низкая отказоустойчивость, по причине того что весь функционал реализован в рамках одного сервиса, проблемы в одной части системы влияют на работу всей системы
- По причине того что решение монолитное, разрабтка будет занимать все больше времени, и привносить проблемы в ранее работающие части системы, требуется высокая культура разработки
- На данный момент монолитное решение работаеть только с одним видов датчиков, что сужает возможности по развитию бизнеса
